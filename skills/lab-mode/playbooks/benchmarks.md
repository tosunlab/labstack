# Benchmarks

"Find the latest benchmarks for X, implement and run them", or run a named benchmark on given models.

**You own finding, running, and checking. The supervisor owns which benchmarks count.**

1. **Find what the field uses now.** Read recent papers and model technical reports on X, filtered by date. Note which benchmarks they report and which baselines they compare against. Leaderboards and aggregators are leads only: they are incomplete, go stale, and can disappear. Date "latest" from the record: the benchmark's version, the paper's version history (an arXiv ID dates only the first version), dated methodology changes on leaderboards, and the date you looked.
2. **Shortlist.** For each candidate state what it measures and whether its tasks require that, saturation (top models tied within noise), contamination risk from item and source dates (fresh contest items may already be online), label quality, overlap with the other picks, whether it is maintained, and whether it is ready to run. Write "unknown" where you don't know. Popularity is not usefulness.
3. **Ask once.** First check the machine you will run on (lab-mode, "Know the machine"). Then one batch: which benchmarks count, the protocol where the request leaves it open (recommend the one used by the work the results will be compared with, taken from its released code, and name that work; if those works disagree or none exists, follow the benchmark's or model's own documentation and label the comparison), the metric, and the cost estimate on that hardware with its basis and ceiling. For a new method, propose baselines from simple to strongest with equal tuning. A budget stated in the request already approves runs within it.
4. **Set up the original protocol.** A published benchmark is prior work: official code at a pinned commit, its prompts, shots, answer extraction, scoring, and data version. Any deviation, including a fix to make it run, goes to the supervisor first. For hosted models, pin the exact model, version, and provider, record the date, and confirm the endpoint accepts the required settings. Record every setting; unknown settings are recorded as missing, never defaulted. An agent's score belongs to the model plus its harness.
5. **Run.** Write a manifest per run. Run detached and resumable. Save per-item inputs, outputs, extracted answers, and scores, with scoring separate from generation. Count infrastructure failures apart from wrong answers. Soon after the run starts, project the total time and cost from the observed rate, and ask before it would exceed the approval.
6. **Check the numbers.** Put each score beside the published score for the same model and setting. A sharp gap in either direction points to setup first: trace one answer that looks correct but was marked wrong through extraction, normalization, and comparison, and re-score the stored outputs before considering any rerun. A defect in your own code may be fixed and rerun within budget; tell the supervisor. A score that looks too good is flagged.
7. **Hand back.** Verdict first. One table: per model and benchmark, our score, n, whether it was rerun or copied, and the published score with its source. Show ties and tiers, not strict ranks. Add measured cost, a few randomly drawn items (input, output, extracted answer, score) with failures included, the command that reruns everything, and every deviation or unverified setting.

**Reply:** the verdict, the table, cost, deviations, and any decision left to the supervisor.
